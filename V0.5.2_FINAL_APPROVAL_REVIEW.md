## 2. Primary approval gate — BLOCKER-2

### CONSISTENT SNAPSHOT: PASS

Actual implementation inspected in `backend/src/routes/analytics.ts`:

- `DbClient` explicitly permits `PrismaClient | Prisma.TransactionClient`.
- `getOrderReportRows()`, `getEmployeeReportRows()`, and `getReconciliationDiagnostics()` accept an injected database client and use that client for their Prisma reads.
- `getClosureControlSummary()` defines one calculation callback and passes the same interactive transaction client (`tx`) to every helper and direct query contributing to:
  - `totalOrderHours`;
  - `totalAbsenceHours`;
  - `totalSettledHours`;
  - `totalEmployeeHours`;
  - `difference`;
  - `diagnostics`;
  - closure-order membership;
  - work-time/absence classification.
- The calculation uses `prisma.$transaction(callback, { isolationLevel: Prisma.TransactionIsolationLevel.RepeatableRead, maxWait: 10000, timeout: 30000 })`.
- No reconciliation helper falls back to the global `prisma` client while this calculation is using `tx`.
- When an existing `Prisma.TransactionClient` is supplied, the helper runs directly on it instead of attempting a nested transaction.

For PostgreSQL, a `REPEATABLE READ` transaction provides a stable transaction snapshot for these reads. Consequently, concurrent report INSERT, UPDATE, or soft-delete operations, order status/completion changes, order assignment changes, and relevant classification changes cannot make different reconciliation queries observe different committed database states during one calculation.

The original inconsistent `READ COMMITTED` multi-read response risk is resolved in production code.

### Transaction/runtime review

- No accidental nested transaction was found.
- No authorization or API contract change was introduced by the transaction wrapper.
- The 10-second acquisition wait and 30-second transaction timeout are explicit. They are operational limits, not a correctness defect; timeout causes an error rather than a contradictory success response.
- The XLSX route still obtains its separately displayed order-report rows outside the reconciliation-summary transaction and then obtains the control summary inside its own transaction. The summary and its diagnostics remain internally consistent, but the surrounding workbook detail can theoretically reflect a nearby committed state. This is a non-blocking export-coherence follow-up, not a recurrence of the returned reconciliation invariant defect.

## 3. Invariant guard

### INVARIANT GUARD: PASS

Before returning every `MISMATCHED` result, production code computes:

```text
round(SUM(diagnostics.contribution), 2)
```

and compares it with the report's two-decimal `difference`, which is computed from:

```text
round(totalSettledHours - totalEmployeeHours, 2)
```

If the values differ, `getClosureControlSummary()` throws `ReconciliationConsistencyError` and does not return contradictory diagnostics. The JSON endpoint maps this to HTTP 500 with:

```json
{
  "code": "RECONCILIATION_CONSISTENCY_ERROR",
  "message": "Błąd spójności danych raportu rozliczenia. Spróbuj ponownie wygenerować raport."
}
```

The client response contains no SQL, connection information, stack trace, Prisma details, or raw database error. Server-side logging contains dates, aggregate totals, and diagnostic count, which is sufficient for investigation without exposing database internals to the API consumer.

Stable endpoint data also verifies Direction A, Direction B, Mixed, and MATCHED behavior, including the endpoint-level invariant for a returned `MISMATCHED` response.

## 4. Concurrency regression

### CONCURRENCY REGRESSION: FAIL

What the new tests prove:

- A unit test verifies that `getClosureControlSummary()` requests `Prisma.TransactionIsolationLevel.RepeatableRead` and that the mocked transaction client's `order`, `workTimeType`, and `workTimeReport` methods are used.
- A guard test makes totals and diagnostics disagree, verifies `ReconciliationConsistencyError`, and verifies the endpoint's controlled `RECONCILIATION_CONSISTENCY_ERROR` response.
- An endpoint test returns a consistent mixed `MISMATCHED` response and verifies that the contribution sum equals `difference`.

What the required concurrency test does not prove:

- The test named `guarantees invariant ... across concurrency edge cases` lists INSERT, UPDATE, soft-delete, and order entering/leaving closure in comments.
- Its implementation calls one helper only twice:
  1. diagnostics contain two missing-order 8-hour rows, producing `-16` against a `-8` difference;
  2. diagnostics are empty, producing `0` against a `-8` difference.
- It does not implement distinct UPDATE behavior.
- It does not implement a soft-delete state transition.
- It does not implement order status/completion entering or leaving closure.
- It does not simulate a stable transaction snapshot with state changes between successive reads, nor does it use two real PostgreSQL sessions to validate visibility semantics.

Thus, the implementation is correct by inspection, but the required representative concurrency regression evidence is incomplete. The claim in `V0.5.2_BLOCKER2_FINAL_REWORK_REPORT.md` that the test covers all four representative cases overstates the actual test implementation.

Required rework is limited to truthful, meaningful regression tests for the named representative transitions. No production-code fix is indicated by this review.
