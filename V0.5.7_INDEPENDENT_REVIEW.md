## 2. Weryfikacja semantyki biznesowej

Implementacja w `backend/src/routes/analytics.ts` (`getOrderReportRows`) prawidłowo rozdziela dwie wielkości:

1. **`periodActualHours` (Godziny rzeczywiste w okresie)**:
   - Liczone wyłącznie dla wpisów mieszczących się w zadanym zakresie dat (`reportDateRange.gte <= date <= reportDateRange.lte`).
   - Zwracane w API jako pole `actualHours` (zaokrąglone do 2 miejsc po przecinku).
   - Prezentowane w UI i eksportach jako kolumna *„Godziny rzeczywiste”*.

2. **`cumulativeActualHours` (Godziny narastająco od początku zlecenia)**:
   - Suma godzin wszystkich aktywnych (nieusuniętych) wpisów od początku zlecenia do końca raportowanego okresu (`date <= reportDateRange.lte`).
   - Wpisy o dacie późniejszej niż `dateTo` są wykluczane już na poziomie zapytania Prisma (`reports: { where: { deletedAt: null, date: { lte: reportDateRange.lte } } }`).
   - Używane **wyłącznie wewnętrznie** do wyliczania:
     - `deviation` (odchylenie),
     - `percent` (% realizacji / wykorzystania).

---

## 3. Weryfikacja interpretacji daty początku zlecenia

- **Zastosowane pole**: `order.orderDate` (biznesowa data zlecenia w schemacie Prisma `Order.orderDate`).
- **Normalizacja daty**: `orderStartDate = order.orderDate ? new Date(`${formatDateKey(order.orderDate)}T00:00:00.000Z`) : undefined`.
- **Interpretacja**:
  Wpisy realizowane w ramach zlecenia są filtrowane warunkiem `!orderStartDate || report.date >= orderStartDate`.
  Dzięki oparciu o `orderDate` (a nie techniczne `createdAt`), wyliczenie jest niezmienne względem momentu fizycznego wprowadzenia rekordu do bazy przez operatora.
  W przypadku braku `orderDate` (np. w środowiskach testowych/mockach), filtrowanie uwzględnia wszystkie historyczne wpisy do `dateTo`.

## 4. Weryfikacja wzorów i obliczeń numerycznych

```typescript
actualHours = Math.round(periodActualHours * 100) / 100;
deviation = Math.round((plannedHours - cumulativeActualHours) * 100) / 100;
percent = plannedHours > 0 ? Math.round(((cumulativeActualHours / plannedHours) * 100) * 100) / 100 : 0;
```

- **Odchylenie (`deviation`)**: Zachowano konwencję `plannedHours - cumulativeActualHours` (wartość dodatnia = pozostałe godziny w budżecie; wartość ujemna = przekroczenie budżetu).
- **Procent (`percent`)**: Zabezpieczenie przed dzieleniem przez zero (`plannedHours = 0` zwraca `0`, brak `NaN` / `Infinity`).
- **Zaokrąglenia**: Wszystkie wartości numeryczne są zaokrąglane symetrycznie do 2 miejsc po przecinku (`Math.round(val * 100) / 100`).
- **Nadrealizacja**: Prawidłowo obsługiwane wartości ujemne dla odchylenia oraz wartości > 100% dla postępu.

## 5. Filtry, statusy i Raport zamknięcia

- **Statusy zleceń (`OPEN`, `CLOSED`, `SUSPENDED`)**: Obliczenia narastające działają identycznie dla wszystkich statusów.
- **`onlyWithHours`**: Filtruje po `row.actualHours > 0` (czyli po godzinach w bieżącym okresie). Zlecenie wielomiesięczne, które miało godziny w przeszłości, ale 0h w wybranym miesiącu, jest poprawnie ukrywane przy aktywnym filtrze.
- **`closureReport` (Raport zamknięcia)**: Warunek widoczności `row.status === OrderStatus.CLOSED || row.actualHours > 0` nadal bazuje na godzinach okresu (`actualHours`), a podsumowanie kontrolne `getClosureControlSummary` nie uległo zaburzeniu.
- **Soft deletes**: Wpisy i zlecenia z `deletedAt != null` są konsekwentnie ignorowane.

## 6. Spójność UI / XLSX / CSV

- **UI (`ReportsView.tsx`)**: Wyświetla `actualHours` (okres), `deviation` (narastająco) i `percent` (narastająco) bezpośrednio ze struktury wierszy zwracanych przez endpoint `/api/analytics/report-by-order`.
- **XLSX (`/api/analytics/export/by-order`)**: Wykorzystuje funkcję `getOrderReportRows`, zapisując te same wartości do komórek Excela.
- **CSV (`handleExportCSV` w `ReportsView.tsx`)**: Mapuje dokładnie te same pola `o.actualHours`, `o.deviation`, `o.percent` ze stanu `reportData`.

Brak rozbieżności pomiędzy interfejsem użytkownika a eksportami.

## 7. Ocena jakości testów

W pliku `backend/tests/analytics.test.ts` dodano dedykowany test:
`keeps period hours while calculating order progress cumulatively through the report end`:
- **Główny scenariusz klienta**: Plan 100h, Lipiec: 30h, Sierpień: 20h, Wrzesień: 10h, Soft-deleted: 8h. Raport za Sierpień weryfikuje: `actualHours: 20`, `deviation: 50`, `percent: 50`. Potwierdza zignorowanie września i usuniętych wpisów.
- **Przypadki brzegowe**:
  - Jednomiesięczne zlecenie `CLOSED` (10h/10h -> dev: 0, 100%),
  - Zlecenie `SUSPENDED` (15h w lipcu + 3h w sierpniu / 50h plan -> dev: 32, 36%),
  - Zlecenie z planem zerowym `plannedHours = 0` (5h w sierpniu, 10h w lipcu -> dev: -15, 0%),
  - Zlecenie historyczne bez godzin w sierpniu (`ZL-HISTORICAL-ONLY`) wykluczane przez `onlyWithHours=true`,
  - Poprawność generowania pliku XLSX (`[20, 50, 50]`),
  - Raport zamknięcia (`closureReport=true`).

Testy nie są tautologiczne — weryfikują zarówno ciało odpowiedzi JSON, zapytania ORM, jak i zawartość binarnego arkusza XLSX.
