## 1. Executive summary

v0.6.0 adds an **in-application, web-based user manual** (`Pomoc` / `Instrukcja`) containing
**REAL, reproducible screenshots** of the actual application UI.

Key decisions:

- Typed TS/TSX help content rendered by a new `HelpView`, integrated into the **existing
  tab-state navigation** (no react-router in v0.6.0).
- Screenshots generated by a new **manifest-driven Playwright pipeline**
  (`npm run docs:screenshots`), committed under `frontend/public/help/`.
- Deterministic, fictional documentation fixture (`seed-docs`, guarded to `*_docs` databases),
  adapted from the deterministic demo seed that already exists on the `demo` branch.
- **Screenshots are a HARD REQUIREMENT.** No mockups, placeholders, or hand-drawn UI.
- **Database migration: NOT REQUIRED** (help is frontend-only; the docs seed is an external
  script, no schema change).

## 5. Help routing/UI architecture

- **No react-router in v0.6.0** (minimal-modification principle per project philosophy).
  Add `currentTab = 'help'` + `helpChapter` persisted in `sessionStorage`, with deep-linking
  via location hash (`#help/<chapter-id>`) so contextual links and prev/next work without a
  router dependency. A real `/help` path + router migration is explicitly deferred (§18).
- Entry points: sidebar item **Pomoc / Instrukcja** (both roles) + navbar `?` button.
  Follows UI Rules order: Title + `BookOpen` Lucide icon → chapter navigation → content →
  prev/next chapter.
- Desktop: left-side chapter navigation. Tablet/mobile (Leader hall-tablet priority):
  top accordion/drawer navigation.
- Header shows `Instrukcja użytkownika — Wersja aplikacji 0.6.0`, version read from
  `/api/version` (same source as the sidebar footer).
- Full-text search: evaluated as not worthwhile for 15 chapters — **deferred** (§18).

## 6. Content format decision

**Decision: typed TS/TSX content modules** (`frontend/src/help/chapters/*.tsx` + `manifest.ts`),
rendered by a new `HelpView.tsx`.

Rationale (based on the actual stack — React + TS, no MD pipeline):

- Zero new dependencies; type-checked, lintable (`npm run lint`), unit-testable.
- Screenshots imported as static assets → **build fails on a missing file** (free broken-image detection).
- Supports headings, numbered steps, warnings/notes, links, contextual anchors via components.
- Version-controlled and reviewable in Git like any other code.

Ruled out: Markdown/MDX (needs loader deps + raw-HTML policy), JSON + generic renderer
(untyped, overengineered for 15 chapters).

## 7. Screenshot automation architecture

```text
frontend/docs-screenshots/
  playwright.config.ts        # Chromium only, 1440x900 base viewport
  manifest.ts                 # source of truth (see §8)
  fixtures.ts                 # login helpers, stability helpers
  capture.spec.ts             # one test per manifest entry
  validate.ts                 # reference checker (CI + release)
frontend/public/help/*.png    # generated assets, committed to Git
```

- New devDependencies **only**: `@playwright/test` (+ browser install on docs/CI runs).
- New scripts in `frontend/package.json`: `docs:screenshots` (regenerate),
  `docs:validate` (reference consistency, no browser needed).
- Runs against a dedicated docs stack: backend on the docs DB + frontend dev/preview build.
- **Never part of `npm test`** — normal frontend tests stay browser-free and fast (§16).

## 8. Screenshot manifest design

Typed record per entry (proposed exact shape):

```ts
interface DocsScreenshot {
  id: string;               // stable screen ID, e.g. "reporting-entry-filled"
  chapter: string;          // chapter ID from §4
  tab: string;              // app tab, e.g. "reporting"
  hash?: string;            // UI state within tab, e.g. report tab id
  role: 'admin' | 'leader'; // authenticated role for capture
  viewport: { width: number; height: number };
  seedState: string;        // required fixture state reference
  uiActions: string[];      // ordered UI actions before capture
  targetFile: string;       // e.g. "raport-hr-01-zmiana.png"
  caption: string;          // caption shown under the screenshot
  stabilityNotes?: string;  // waits, masks, animation handling
}
```

- `capture.spec.ts` iterates the manifest; `validate.ts` parses chapter modules for referenced
  files and **fails on missing or unreferenced images**.
- Naming: `<chapter>-<nn>-<slug>[@tablet].png`.

## 10. Documentation fixture/data strategy

- Create `backend/prisma/seed-docs.*` (+ `seed-docs-data.ts`) by **porting/adapting the
  deterministic generator from the `demo` branch** (`seed-demo-data.ts`): fixed UUIDs, fixed
  bcrypt salt, `FIXED_TIMESTAMP`, fictional employees/orders, fixed date range.
  (Alternative if the demo seed gets merged to `development` first: reuse it directly with a
  docs-specific overlay — decide at Increment 2 kickoff.)
- Guard: script runs **only** when the database name ends in **`_docs`** (mirror of the
  demo `_demo` guard, incl. secret-safe URL validation + unit tests). Rejects production /
  client databases before connecting.
- Fixed documentation dates: a Tue–Thu inside the seeded range (avoids weekends/holidays).
- Fictional data only (fake companies, fake employee names like the demo set).
- `npx prisma migrate reset` stays forbidden — the docs DB is created empty, then
  `migrate deploy` + `seed:docs`.

---

## 11. Privacy/sanitization strategy

1. Fictional-only dataset by construction (no client employee names, orders, or personal data).
2. Fixed non-real credential hash; no real passwords/tokens/connection strings in the repo.
3. DB-suffix guard refuses non-`*_docs` databases **before** connecting and never echoes
   `DATABASE_URL` or secrets (same pattern as the demo guard's tests).
4. Login screenshot uses empty fields; captures never include tokens, passwords, or private URLs.
5. Every screenshot is a committed file → reviewed in the normal PR process.

---

## 12. Screenshot stability strategy

- Pinned Chromium, fixed viewports (1440×900 desktop; 834×1112 tablet variants).
- Single locale/timezone; animations + caret blink disabled via injected CSS.
- `networkidle` + deterministic waits; seeded DB reset per run; fixed dates (never "today").
- Volatile footer/version strings masked where needed; stable filenames; committed baselines
  so diffs appear only on intentional UI change.

- `docs:validate`: manifest ⇄ files ⇄ chapter-reference consistency (missing/unreferenced
  image fails the check); wired into release verification scope.

## 16. CI/release workflow

- **On-demand regeneration** (`npm run docs:screenshots`) during documentation changes only.
- CI runs the fast, browser-free `docs:validate` (referenced screenshots exist).
- Pre-release checklist: re-run generation + visual review **iff** any user-visible screen
  changed in the release.
- Normal `npm test` (backend + frontend) **never launches browsers** — development stays fast.

## 18. Scope: MUST / SHOULD / DEFER

- **MUST HAVE for v0.6.0:** integrated help (all roles); ~15 chapters (§4); ~20 REAL
  screenshots (§9); reproducible `docs:screenshots`; deterministic non-production fixture;
  chapter navigation + prev/next + version header; 5 contextual links; tests + `docs:validate`;

## 20. Risks and mitigations

| Risk | Mitigation |
|---|---|
| No-router deep-link fragility | hash-based chapters + tests |
| Playwright flakiness | pinned browser, `networkidle`, fixed data/dates, disabled animations |
| Demo-seed port divergence | single shared data module; docs-specific overlay; decide reuse-vs-port at Increment 2 |

| Documenting the wrong UI | chapters written from components, reviewed against the running app |
| Privacy leak in captures | fictional fixture + DB guard + PR image review (§11) |
| Scope creep (search, videos, i18n) | explicit DEFER list (§18) enforced in review |
