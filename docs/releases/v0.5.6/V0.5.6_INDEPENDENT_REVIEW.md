## Root cause and business-rule assessment

The stated root cause is correct. Before this change, closure-mode qualification was limited to OPEN orders and CLOSED orders whose current `completionDate` fell in the report range. A report logged in August could therefore remain in employee totals after the order was closed on 2026-09-10, while its order was absent from order totals.

Both changed functions add the same third qualification branch: an OPEN or CLOSED order with at least one non-deleted `WorkTimeReport` dated in the report range. The actual selected reports are still limited to the range before `actualHours` is summed. Thus it satisfies the required historical-stability rule without introducing a second aggregation path.

## `getOrderReportRows()` assessment

For `closureReport=true`, the new Prisma `OR` condition is structurally correct.

- **A. CLOSED; completion after `dateTo`; hours in range:** included, and its 20 h + 15 h are returned as `actualHours = 35`.
- **B. CLOSED; completion after `dateTo`; no hours in range:** not included through the new branch.
- **C. OPEN; hours in range:** unchanged and included.
- **D. CLOSED; completion in range:** unchanged and included, including zero-hour closed orders.
- **E. CLOSED; completion before `dateFrom`:** unchanged when it has no in-range report (hidden); it is now included if it has an in-range non-deleted report. This is a deliberate consequence of the stated report-date-based stability rule and prevents legitimate late corrections from producing a reconciliation gap.
- **F. SUSPENDED:** remains excluded in closure mode; the new branch explicitly permits only OPEN/CLOSED.
- **G. Soft-deleted report:** cannot qualify an order because `reports.some` requires `deletedAt: null`; selected/summed reports have the same filter.
- **H. Report outside the range:** cannot qualify via the new branch and is not summed.
- **I. Double counting:** no. Prisma OR changes membership only; the included relation is range-filtered and each selected report is reduced once.

`closureReport=false`, ordinary status filtering, and `onlyWithHours` remain on their existing paths. In closure mode, status and `onlyWithHours` were already intentionally ignored by the route, and that behavior is unchanged.

## `getReconciliationDiagnostics()` assessment

The diagnostics query uses an equivalent predicate: `deletedAt: null`, OPEN/CLOSED status, and `reports.some` with the same inclusive date boundaries. An August report for a currently CLOSED order completed on 2026-09-10 therefore has its order id in `orderIdsInClosure`, so its non-absence contribution becomes zero rather than `-35` with reason “Zlecenie nieobjęte raportem zamknięcia”.

The other qualification semantics are as assessed above, including SUSPENDED exclusion and soft-delete protection.

## Consistency and XLSX/export assessment

The two functions express equivalent closure membership rules, differing only in local construction of the same range values. `getClosureControlSummary()` obtains `ordersHours` by calling `getOrderReportRows()` and then calls diagnostics with the identical date parameters. Therefore the production paths cannot diverge for the new historical-order rule.

`GET /api/analytics/report-by-order?closureReport=true` calls `getOrderReportRows()`. `GET /api/analytics/export/by-order?closureReport=true` calls that same function to construct its spreadsheet rows. The export path therefore inherits the corrected order membership and range-limited 35 h total; no separate XLSX query can omit the order.

## Regression-test assessment

The parameterized closure report-by-order case for `ZL-013` is meaningful: its mock reads `args.where.OR[2]` and its `reports.some` details. On pre-fix code where the third branch did not exist, this mock excludes the post-period CLOSED order, so the expected visible row with `actualHours = 35` would fail. This covers the report-by-order behavior.

The newly added exact reconciliation test, despite asserting the required 35 h, `difference = 0`, and `MATCHED`, is **not a valid regression test for the implementation**. Its `prisma.order.findMany` mock returns the CLOSED order whenever `args.where.OR` exists. The pre-fix implementation also has an OR (with only the original two branches), so the test would return the order and pass before this change. It does not inspect the third branch or evaluate the query predicate.

The added contrast test also does not demonstrate the new source predicate: its mock independently reimplements the desired three-branch selection, rather than deriving its outcome from the queried `OR` supplied by the code under test. Its zero-total expectation would pass before the patch as well. The contrast condition itself is correct, but the test is not proof against regression.

The export test exercises the export endpoint generally, and the export implementation correctly reuses `getOrderReportRows()`, but there is no focused XLSX assertion for order `530-8-49` / `ZL-013` and 35 h.

### Minimal required rework

Repair the two reconciliation regression mocks so that they faithfully apply the received `where.OR` (or explicitly assert that the third branch contains `status IN [OPEN, CLOSED]` and `reports.some { deletedAt: null, date: range }`). The exact 35 h summary test must fail on the pre-fix two-branch query and pass only with the new branch. The contrast test should likewise use the received predicate and prove the post-period CLOSED order with only out-of-range/deleted reports is excluded. No production-logic change is required for this finding.

## Status/filter, soft-delete, and semantic-regression assessment

Static review and the passing suite confirm no change to the standard report (`closureReport=false`), its status parsing, or `onlyWithHours`. Closure-mode OPEN, in-range CLOSED, SUSPENDED, deleted order, zero-hour closed order, and date-boundary cases continue to have coverage. The new conditions contain `deletedAt: null` both for qualification and for the reports used in totals. No accidental SUSPENDED inclusion or out-of-range hour aggregation was found.

## Performance and index assessment

Prisma will express `reports.some` as a relational existence condition. That is appropriate logically and avoids loading reports merely to qualify an order. However, the author report's statement that it uses “indexed `orderId` + `date`” is **not supported by `backend/prisma/schema.prisma`**: `WorkTimeReport` declares no `@@index`, and there is no schema-declared composite index on `(orderId, date)` (nor an index visibly covering `deletedAt`). This is a non-blocking observation for the present feature; performance has not been measured against production data and should not be represented as proven negligible or index-backed.
