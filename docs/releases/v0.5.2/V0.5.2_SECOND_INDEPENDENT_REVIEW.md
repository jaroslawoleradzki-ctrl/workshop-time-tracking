## 5. NS incident assessment

### End-to-end current path

1. `ReportingPanel` loads active employees, open orders, and work-time types sequentially.
2. The selected order is a full object from `/api/orders/active`; editing its text clears that selection.
3. Frontend validation requires a selected order when the fetched type has `requiresOrder=true`.
4. The preflight warning request does not validate the calendar or order. Its failure does not block the subsequent save.
5. CREATE sends `date`, `employeeId`, `selectedOrder.id` (or null), numeric hours, selected type code, and `missingCard` to `POST /api/reports`.
6. Backend validates required values/positive hours, normalizes the date to a UTC date key, loads employee and WorkTimeType, obtains the authoritative Company Calendar decision, validates the free-day rule, verifies a required non-deleted order, calculates warnings, inserts inside the advisory-lock transaction, attempts the non-fatal audit write, and returns HTTP 201.
7. Frontend parses JSON; for non-2xx it throws `data.message`, and the catch writes the message to the visible `validationError` alert.

For expected seeded NS data (`requiresOrder=true`, `isAbsence=false`) and a non-empty valid order ID, Sunday 2026-09-06 is accepted by the current backend rule. A Company Calendar override marking Sunday as working cannot explain rejection because a working day immediately passes calendar validation.

The branch does not identify why production produced neither a record nor a visible error. It proves only the mocked backend happy path. It does not verify the actual deployed frontend payload, `/api/version`, production NS flags, actual order state, response body/status, proxy behavior, backend logs, transaction outcome, or audit failure.

## 7. Reconciliation mathematical verification

### Stable-dataset algebra

For each active report in one stable dataset:

| Record state | Orders side | Absence side | Employee side | Signed contribution (`settled - employee`) |
|---|---:|---:|---:|---:|
| Non-absence, order included in closure | +h | 0 | -h | 0 |
| Non-absence, missing/excluded order | 0 | 0 | -h | -h |
| Absence, no included order | 0 | +h | -h | 0 |
| Absence, included order | +h | +h | -h | +h |

This correctly handles:

- Direction A (`employee > settled`): missing order and order outside closure produce negative contributions.
- Direction B (`settled > employee`): absence with an included order produces a positive contribution from double counting.
- Matched entries and zero-hour entries: contribution zero and omitted.
- Duplicate records: each record contributes exactly as each record contributes to the totals; no separate deduplication is appropriate here.
- Hours rounding: DB hours have two decimal places and the displayed totals/difference use two-decimal rounding; for one stable valid dataset the signed sum reconciles under those rules.

### BLOCKER — invariant is not guaranteed by the endpoint

`getClosureControlSummary()` obtains order totals, absence rows/types, and employee totals in separate Prisma calls, then—only after detecting a mismatch—`getReconciliationDiagnostics()` independently re-reads all reports and closure order IDs (and performs an unused type query). These calls are not in a repeatable-read transaction and do not share input records.

Under PostgreSQL/Prisma READ COMMITTED behavior, a concurrent report insert/edit/delete or order status/completion change can occur between those calls. Example: an initial `-8 h` mismatch is calculated; before diagnostics are read, another unassigned 8 h entry is inserted. The response can contain `difference = -8` but diagnostic contributions summing to `-16`. An order moving into/out of the closure set creates the same class of failure.

There is no final server-side assertion or error state when `round(sum(contribution), 2) !== difference`.

The new test named as a math invariant imports `getReconciliationDiagnostics()` directly and compares its sum with a hard-coded `8`; it does not call `getClosureControlSummary()` and compare the two fields returned by the same response. Direction A/B unit examples pass, but missing/excluded order, mixed offsets, rounding, endpoint-level identity, and concurrent snapshot behavior are not comprehensively tested.

Therefore the required production invariant is not guaranteed.

- Severity: **BLOCKER**
