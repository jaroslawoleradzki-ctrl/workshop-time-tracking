### HIGH-2 — Diagnostics do not always explain `employeeHours - settledHours`

- Severity: **HIGH**
- File: `backend/src/routes/analytics.ts:468-532, 535-632, 652-725`; `backend/prisma/schema.prisma:45-56`; `backend/src/routes/work-time-types.ts:67-99`
- Problem: the diagnostic classifier is not derived from exactly the same signed contribution used to calculate the two totals.
- Evidence:
  - An entry whose order is in closure contributes to `ordersHours`, regardless of time type.
  - Every `isAbsence=true` entry also contributes to absence hours.
  - The employee total counts every active entry once.
  - Therefore an absence linked to an included order is counted twice in settled hours but once in employee hours, producing Direction B (`settled > employee`). This state is permitted: `isAbsence` and `requiresOrder` are intentionally independent, and admins can edit `isAbsence` even for system types.
  - `getReconciliationDiagnostics()` ignores all absences, so Direction B returns no explanatory rows. In a mixed month, positive double-counting offsets negative unassigned rows; the displayed row-hours sum can be larger than `employeeHours - settledHours`.
  - Zero-hour non-absence records without/in an excluded order are returned even though they cause no difference.
  - `absenceTypeCodes` is queried and constructed at lines 581-586 but never used.
  - The MISMATCHED test at `backend/tests/analytics.test.ts:1127-1211` does not assert the returned diagnostics, their reasons, or that their signed sum equals the difference.
- Impact: diagnostics can show too many rows, too few rows, or no rows for a real mismatch. Users can be sent toward records that do not reconcile to the displayed number.
- Recommended fix: compute a signed per-record contribution using the same closure-membership and absence semantics as the totals, return only non-zero contributions, include direction/sign, and assert `sum(diagnostic contributions) == totalEmployeeHours - totalSettledHours` (within the same rounding policy) across negative, positive and mixed cases.

## 4. Production NS path analysis

### End-to-end trace

1. `ReportingPanel` loads active employees, open orders and work-time types.
2. NS order field is rendered only if the fetched NS record has `requiresOrder=true`.
3. Choosing an autocomplete result stores the complete order object. Typing afterwards clears `selectedOrder`; changing work type itself does not clear the selected order.
4. Submit finds the selected type and requires a selected order when `requiresOrder=true`.
5. Preflight `/api/reports/check-warnings` does not validate calendar/order. A non-OK response is ignored and save proceeds; network errors are logged and save proceeds.
6. Create payload sends `orderId: selectedOrder?.id || null`. Since selection comes from `/api/orders/active`, its normal format is the database UUID string. No component test asserts the NS payload.
7. Backend create route validates required fields and positive hours, normalizes the date to UTC midnight, validates active employee, loads WorkTimeType from DB, loads Company Calendar, applies `code !== G && !isAbsence && requiresOrder && Boolean(orderId)` on a free day, then validates the referenced non-deleted order.
8. It calculates warnings, acquires a PostgreSQL advisory transaction lock, creates the report, logs an audit outside the insert transaction, and returns 201 JSON `{report, warnings}`.
9. Frontend parses JSON, throws `data.message` for non-2xx, shows success and refreshes on 2xx, and writes thrown errors to the visible `validationError` alert.

### CREATE versus UPDATE

- Both routes perform dictionary, calendar and required-order checks.
- CREATE additionally validates that the employee exists/is active and serializes the write with the copy-last-day lock.
- UPDATE does not validate the target employee and does not take that lock. This is not an explanation of the reported CREATE failure but is a separate pre-existing contract difference.
- The candidate did not modify either route.

### Feedback behavior

For a normal JSON error, the current frontend should display the backend message. This behavior already existed in the base. No evidence explains the production observation of no message. Non-JSON/empty responses are caught and should show the thrown parsing error, though it may be technical rather than friendly. There is no save-in-flight disabled state, so duplicate submissions are possible, but that also does not explain the reported silent non-save.

### NS result

**ROOT CAUSE NOT IDENTIFIED.**

The candidate proves the expected backend happy path under mocks. It does not establish the deployed payload, deployed version, production dictionary/calendar/order state, actual response, persistence outcome or visible UI feedback. The issue must not be called FIXED.

## 9. Reconciliation diagnostics assessment

For the simple production Direction A case—one active, positive, non-absence 8 h entry with no order or an order outside the closure set and no offsetting Direction B entry—the backend would return that record and its hours would explain `employeeHours - settledHours = 8`.

It is not guaranteed generally. The exact accounting identity is:

- non-absence + included order: counted once on both sides;
- non-absence + no/excluded order: employee-only (negative displayed `settled - employee`);
- absence + no/excluded order: counted once on both sides;
- absence + included order: counted twice in settled, once in employee (positive displayed `settled - employee`).

Because the last state is allowed and not diagnosed, and because zero/non-contributing records can be listed, the sum of displayed diagnostic hours is not guaranteed to equal `employeeHours - settledHours`.

Direction B is not merely “orders with hours not reflected in employee reports”—order hours themselves come from employee report rows. It can arise from double-counting an absence tied to an included order. Missing Direction B is therefore not safely dismissible as low probability without first preventing this data state or changing the aggregation. The UI's generic text suggests it can guide the user, while it does not show rows at all.

Assessment: **HIGH; must be corrected before merge**.
