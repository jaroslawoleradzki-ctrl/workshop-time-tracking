## FRONT-001 re-review

**Status: RESOLVED.**

The component now maintains a local form mode of `pristine`, `modified`, or `editing`. A context-reset effect runs only when the employee/date context changes; it no longer depends on `calendarDecision`. A separate defaulting effect applies a type only when all of these are true:

- dictionaries and current employee are present;
- the form remains pristine; and
- `calendarDecision.date === currentDate`.

A context reset reads a cached decision only after the same date check; otherwise it sets the type blank until the current date's decision arrives. Thus a prior-date decision is not reused for an uncached new date.

The original fetch effect's `isCurrent` cleanup and `activeCalendarFetchDateRef` check still reject stale old-date results. A stale response can therefore not apply a type to the new date. Even in an event-loop interleaving where a prior response updates state before effect cleanup, the new defaulting effect rejects it because its returned date does not equal `currentDate`.

Manual type selection, order selection/search, hour entry, and missing-card changes mark a pristine new form modified. `handleEditEntry` marks the form editing before it loads saved state. Consequently a completion for the current date cannot replace manual values, clear the order/hours/missing-card state, or clear `editingReportId`. A Cancel or successful Save deliberately resets the form to pristine, where applying the known current-date default is appropriate.

The rework does not alter the existing calendar fetch fallback or stale-request guard.

## Regression-test quality

The focused tests in `frontend/src/test/ReportingPanel.test.tsx` use controllable deferred promises, not timing-only final-state checks.

- The manual-selection test changes to an uncached date, proves the interim blank state, selects `UW`, then resolves the *current* date response and asserts `UW` remains.
- The edit test delays the current date, enters an existing `NS` report, and after resolution asserts edit heading/save mode, type, order, hours, and missing-card state all remain.
- The prior-decision test first caches Sunday/`NS`, changes to unresolved Tuesday, asserts blank rather than `NS`, then resolves Tuesday and asserts `G`.
- The pristine-form test asserts blank while Sunday is unresolved, then asserts `NS` after resolution.
- The existing slow-old-date regression remains and confirms a late old non-working response cannot replace the newer date's `G`.

The first three tests would fail on the pre-fix reset path: it reset on current-date completion and reused `calendarDecision` from the previous date. The pristine-form test also rejects the old implementation's interim fallback/previous-decision behavior while preserving required async defaulting.
