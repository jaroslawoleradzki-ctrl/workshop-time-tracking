## Backend calendar review

`parseDateString` accepts only valid `YYYY-MM-DD` values, creates a UTC-midnight date, and validates round-trip components. `formatDateString`, holiday lookup, and weekend determination use UTC. For `2026-09-17`, the endpoint therefore queries and returns that exact calendar day; no local-time conversion moves it to an adjacent day.

`getWorkingDayDecision` applies company override first, public holiday second, and UTC weekday/weekend last. Missing overrides use the base calendar. The single-day endpoint rejects invalid dates and is behind JWT authentication; calendar mutations require an administrator. The report create/update route rechecks calendar eligibility server-side before persistence. No inactive or soft-deleted calendar-day state exists in the schema.

The route's general report-date parsing uses legacy `new Date(date)` handling, but the v0.5.8 calendar endpoint and service use the strict UTC utility. This review found no timezone shift in the calendar decision path.

## Frontend default-selection and async review

For a settled decision, `getDefaultWorkType` implements the documented rules: working day -> existing `G`; weekend non-working day -> existing `NS`; other non-working day or a missing required type -> blank. Lookup is by exact code, not list position. `code` is the work-time-type primary key, so duplicate codes cannot occur; API ordering is immaterial. There is no inactive/deleted state on this model. Missing `G`/`NS` produces blank rather than an arbitrary type.

The async guard correctly rejects a result for an earlier date. It does not, however, protect user state from a result for the *current* date:

1. After a date change to an uncached date, `resetForm` uses `calendarCacheRef.current.get(currentDate) || calendarDecision`. The second operand can be the previous date's decision.
2. When the current date's request completes, setting `calendarDecision` retriggers the reset effect. `resetForm` resets work type, order, hours, and `editingReportId` without determining whether the user manually changed the form or entered edit mode while the request was in flight.

Thus old-response suppression is present, but current-response protection is not. This is the basis of finding FRONT-001.

## Edit and data-integrity assessment

Clicking Edit initially loads the saved work-time type, hours, order, and missing-card flag. Merely opening a report or entering edit mode sends no write; only an explicit POST/PUT from Save changes a record. There is no silent historical database mutation.

Nevertheless, FRONT-001 can replace an edit form's local values before the user saves, creating a risk of an unintended update if the user proceeds. On a non-working day the server restricts invalid `G`/absence reports, but a wrong otherwise-permitted type can still be selected and submitted. This is a UI/data integrity concern, not an authorization bypass.

## Findings

### FRONT-001 — MAJOR — current calendar completion can overwrite user/edit state

Affected file: `frontend/src/components/ReportingPanel.tsx` (calendar fetch effect, `resetForm`, and reset effect).

Reproduction: select a date whose calendar decision is not cached and delay its `/api/company-calendar/day/:date` response. Before it returns, choose a work type manually, or click Edit on an existing entry. When the delayed response returns, the `calendarDecision` state update retriggers `resetForm`; it replaces the selected work type and clears edit mode and other entered fields. Also, the initial reset for that new date can use the previous date's decision.

Why it matters: the UI can display or save a type based on the wrong date, can discard a deliberate choice, and can turn an edit into a new-entry form. The old-date response guard does not address this current-date scenario.

Recommended correction: only use a decision whose `date` equals `currentDate` (otherwise use a local fallback or wait), and apply an asynchronous default only to a pristine new form. Track manual/edit intent so a completed request cannot reset it. Add deterministic deferred-request tests for manual selection and editing while the current-date request is unresolved.

### DOC-001 — MINOR — user guide omits calendar-aware exceptions

Affected file: `docs/user-guide.md`.

The guide says weekdays default to `G` and Saturday/Sunday to `NS`, without the implemented exceptions for public holidays, company days off, working weekends, and missing types. It can mislead operators about actual behaviour.

Recommended correction: after resolving the functional finding, update the guide with the implemented calendar-aware precedence and safe blank fallback.

### OBS-001 — OBSERVATION — fallback is cached for the component lifetime

Affected file: `frontend/src/components/ReportingPanel.tsx`.

On a transient calendar-endpoint failure, the local fallback is cached for that date and is not retried until remount. The backend still validates a submitted report, so this does not bypass rules, but a temporary outage can leave the UI with a less accurate suggestion. Consider a later UX decision on retry/cache expiry; it is not a release blocker by itself.

Findings totals: BLOCKER 0, MAJOR 1, MINOR 1, OBSERVATION 1.

Correct that defect and add focused regression coverage before manual acceptance. This verdict is not a merge approval.
