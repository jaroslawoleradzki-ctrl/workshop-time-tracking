## Findings

### V060-IR-01 — MAJOR — Help hash overrides existing tab persistence

- **Location:** `frontend/src/App.tsx:59-63`, `164-183`, and the non-Help sidebar button handlers near `371-520`.
- **Problem:** Opening Help writes `#help/<chapter-id>`. Selecting Reporting, Reports, Orders, or another application tab only changes `currentTab`; the Help hash remains. On reload, the initializer sees `#help/` and reopens Help even though `sessionStorage.current_tab` contains the selected application tab. The `hashchange` listener also ignores a hash cleared by browser Back, leaving the current Help chapter displayed.
- **Impact:** Existing tab-state navigation is not reliably restored after visiting Help; browser history and the visible tab can disagree.
- **Required correction:** Keep hash and tab selection in sync when leaving Help and when navigating Back/Forward, with tests for Help → normal tab → reload and Help chapter → browser Back.

### V060-IR-02 — MAJOR — `docs:validate` cannot establish manifest/reference consistency

- **Location:** `frontend/docs-screenshots/validate.ts:6-10`, `frontend/src/help/chapters.tsx:11-17`.
- **Problem:** The validator considers a manifest target referenced if its filename occurs anywhere in the chapter source. The filename remains in `HELP_SCREENSHOTS` even when the rendered `<img>` is removed. Its regex only discovers literal `/help/file.png` strings; it cannot resolve the actual `` `/help/${HELP_SCREENSHOTS.login}` `` reference. It also never checks that a manifest chapter ID exists.
- **Impact:** The fast validation command can pass with an unused screenshot or an invalid manifest chapter, contrary to the plan's manifest ↔ file ↔ rendered-reference gate.
- **Evidence:** In isolated scratch copies, deleting the target PNG failed validation as expected, while removing the rendered figure but retaining the filename constant **passed**, and changing the manifest chapter to a nonexistent ID also **passed**. The original files passed.
- **Required correction:** Make chapter screenshot references explicit, typed data that the browser-free validator can compare with manifest entries and files. Test missing targets, unreferenced assets, invalid chapter IDs, and unmanifested references.

### V060-IR-03 — MAJOR — Documentation seed is fictional but not deterministic

- **Location:** `backend/prisma/seed-docs.ts:7-15`; generated defaults in `backend/prisma/schema.prisma:11-25,65-84`.
- **Problem:** The seed fixes the order date and one employee ID, but lets Prisma generate random user and order UUIDs and current `createdAt`/`updatedAt` values. Repeated upserts also leave an existing docs user's changed password hash untouched. Two fresh docs databases, or a rerun after such a change, therefore do not have identical canonical fixture state.
- **Impact:** The fixture does not meet the approved plan's repeatable seed criterion and is not a reliable basis for later authenticated screenshots. The current anonymous login PNG is unaffected.
- **Required correction:** Use fixed IDs, timestamps, and complete fixture fields for the documentation rows; make reruns converge to the same state, or reject a pre-populated noncanonical docs database without deleting data. Add an idempotence/determinism test.

### V060-IR-04 — MINOR — Stability CSS is discarded before capture

- **Location:** `frontend/docs-screenshots/fixtures.ts:2`, `capture.spec.ts:5,10`, `manifest.ts:2`.
- **Problem:** `prepareStablePage` injects animation/caret-disabling CSS and then the test reloads the page. Reload removes the injected style. The manifest's stability note says animations are disabled, although they are not disabled at capture time.
- **Impact:** Future screenshots with animated UI or focused fields may vary. The current login capture was byte-identical in this review.
- **Required correction:** Apply the stability style after the final reload, or install it for each navigation, and verify it is active before capture.

### V060-IR-05 — MINOR — Implementation report has stale and inaccurate statements

- **Location:** `docs/releases/v0.6.0/V0.6.0_USER_GUIDE_FOUNDATION_REPORT.md:12,36,50`.
- **Problem:** It still calls the implementation uncommitted, includes a sample connection string despite the plan's no-connection-string documentation rule, and says no existing Docker volume was modified. Creating a database in the existing PostgreSQL container necessarily changed its mounted data volume, although no volume was deleted and no existing database was modified. Its claim of a deterministic pipeline also needs qualification until V060-IR-03/04 are fixed.
- **Impact:** Reviewers receive an inaccurate implementation SHA and storage/safety account.
- **Required correction:** Record the feature SHA, describe precisely that only a new docs database was created in the existing PostgreSQL volume, remove the connection-string example, and qualify fixture/stability claims.
