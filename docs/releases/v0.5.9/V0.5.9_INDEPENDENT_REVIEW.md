## Assessment

### Data model and migration — PASS

`WorkTimeReport.workShift` is a nullable `WorkShift` enum (`FIRST`, `SECOND`) tied to each individual report entry. The enum is cleanly extensible with `THIRD` in a later migration. The migration only creates the enum and nullable `work_shift` column; it does not update historical rows, reset, truncate, reseed, or otherwise destroy data. A direct upgrade from v0.5.6 is structurally compatible because all preceding migrations remain in sequence and this addition is nullable. Absence-range creation explicitly writes `null`.

### Backend business rules — FAIL

POST and PUT correctly enforce FIRST/SECOND for worked entries and null-only shift for absence types; reads expose `workShift`, including historical nulls. However, copy-last-day uses `createMany` directly and allows a historical worked source row with null shift to create a new worked row with null shift. This bypasses the mandatory-shift rule and is a release-blocking rework item (BACK-001).

No import path creates `work_time_reports`; the only creation paths found are POST reports, absence-range, and copy-last-day.

### Frontend shift state — PASS

The selector is semantic (`isAbsence`), offers I/II for work, disables and clears state for an absence, submits null for absence, preserves FIRST/SECOND on edit, displays historical null as “Brak danych o zmianie”, and requires an explicit selection before a historical-null entry can be saved. Calendar responses are guarded by date/current-form checks and only alter a pristine new form, preserving v0.5.8 behaviour.

### Copy/duplication — FAIL

FIRST and SECOND source rows preserve their values and absence copies are forced to null without changing hours or transaction/audit handling. Historical null worked sources are not rejected or otherwise resolved before `createMany`; the new copied entry remains null. See BACK-001.

### HR monthly report and XLSX — PASS

Employee aggregation adds the source report's `hours` exactly once to FIRST, SECOND, or historical-unspecified only when `workTimeType.isAbsence` is false. Thus absences contribute to neither shift total; overtime is not double-counted, and the existing overall and non-overtime totals remain independently calculated. Dynamic type columns remain. The XLSX uses the same row calculation, emits numeric shift cells, conditionally includes “Brak danych o zmianie”, and retains frozen row 6/autofilter behavior. Tests deserialize a generated XLSX and assert headers, values, frozen pane, and autofilter.

### Absence, calendar, reconciliation, and cumulative analytics — PASS

Absence-period logic is not changed except that absence-range writes null. The report retains semantic `isAbsence` filtering, ART188 coverage, grouping/working-day/calendar bridging, and no shift dimension. Existing v0.5.8 calendar defaults and stale-response protections are preserved. Closure-control/reconciliation and cumulative order logic are unchanged; targeted regression tests pass.

## Verdict rationale

**C — REWORK REQUIRED BEFORE MANUAL ACCEPTANCE.** There are no destructive migration, security, or data-loss findings, so verdict D is not warranted. BACK-001 is nevertheless a MAJOR correctness and server-side enforcement defect: historical worked records are expected after upgrade and copy-last-day can manufacture new unclassified worked records from them. Rework, tests, and a fresh independent review are required before manual acceptance.
