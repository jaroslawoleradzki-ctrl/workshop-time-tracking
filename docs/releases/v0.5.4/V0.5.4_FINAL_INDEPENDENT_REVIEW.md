## 3. WKU i typy własne

Potwierdzone w migracji:

- nowy `WKU`: `requires_order=false`, `is_absence=true`, `is_system=false`;
- istniejący `WKU`: zmieniają się wyłącznie obie zatwierdzone flagi; `name` i `is_system` pozostają bez zmian;
- migracja nie modyfikuje `work_time_reports`;
- ponowne wykonanie nie zmienia `updated_at`, jeżeli flagi są już poprawne (warunkowy `CASE` w. 10–13).

Wykonywalny test upgrade'u potwierdził custom WKU o nazwie `Wojsko / WCR Klienta`, pozostający `isSystem=false`; kontroluje również pięć historycznych raportów. Test API sprawdza, że custom WKU można usunąć (gdy brak raportów) i edytować ([canonical-work-time-types.test.ts](backend/tests/canonical-work-time-types.test.ts), w. 506–547). UI blokuje delete tylko dla `isSystem=true` i pozostawia Edit dostępne dla obu statusów.

Dla OP i NN test PostgreSQL potwierdza po upgrade niezmienione `name`, `isSystem`, `requiresOrder` i `isAbsence`. Pozostałe wskazane kody (`NU`, `NUN`, `NUP`, `UB`, `UO`, `UPP`) są bezpośrednio bezpieczne w aktualnym kodzie, ponieważ ani SQL migracji, ani seed ich nie odczytuje ani nie zapisuje. Ich pełna kolizja upgrade nie ma jednak osobnego wykonawczego przypadku testowego — jest częścią wymaganego uzupełnienia B4.

## 10. Znalezione problemy

### F1 — krytyczna ścieżka upgrade deploymentu nie jest wykonawczo testowana

- **Severity:** High / blocker.
- **Lokalizacja:** `backend/tests/executable-database-migration.test.ts:81–92, 254–270, 333–349`; rzeczywista referencja: `backend/docker-entrypoint.sh:4–8`.
- **Problem:** upgrade przygotowuje stan v0.5.3 przez ręczne wykonywanie wszystkich SQL i uruchamia v0.5.4 przez raw `psql`; seed uruchamia z TS przez `npx ts-node`. Production uruchamia `prisma migrate deploy`, potem skompilowany `node dist/prisma/seed.js`.
- **Dlaczego istotny:** B4 wymaga rzeczywistego przejścia migration → production seed. Ręczna ścieżka omija tracking/checksum/order Prisma i artefakt używany przez kontener; wynik 4/4 nie stanowi dowodu release-readiness tej ścieżki.
- **Wymagana poprawka:** test upgrade powinien utworzyć rzeczywisty stan przed v0.5.4 z historią `_prisma_migrations`, następnie uruchomić `prisma migrate deploy` na kandydacie i `node dist/prisma/seed.js` po `npm run build` (lub dokładnie entrypoint w disposable kontenerze). Nie wolno używać raw `psql` do migracji kandydata ani `ts-node` zamiast prod seed.
- **Wymagany test regresyjny:** jeden rzeczywisty upgrade path, a następnie jego powtórzenie, z custom `WKU`, `OP`, oraz osobnymi custom `NN`, `NU`, `NUN`, `NUP`, `UB`, `UO`, `UPP`; asercje przed/po dla `name`, `isSystem`, obu flag, możliwości API edit/delete oraz niezmienionych historycznych `work_time_reports`. Fresh path należy uruchamiać tym samym compiled seed.
