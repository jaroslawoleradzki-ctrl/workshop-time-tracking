## 8. WKU assessment

The candidate correctly encodes the required WKU business flags `requires_order=false` and `is_absence=true` in both migration and seed. Dynamic absence aggregation means WKU will then participate in closure control and the HR absence report. The revised reconciliation reason also avoids calling an optional-order, non-absence record “Brak zlecenia.”

The WKU solution is nevertheless unsafe as submitted because it additionally forces `is_system=true` and the production seed forces the name `Wojsko`. Neither mutation is part of the stated WKU decision. The known production WKU record was `is_system=false`; converting it removes deletion and `requiresOrder` editing capabilities.

## 9. Migration safety assessment

Location: `backend/prisma/migrations/20260908120000_canonical_work_time_types_hardening/migration.sql:3-25`.

- The SQL is repeatable with respect to final flag values through `INSERT ... ON CONFLICT DO UPDATE`; rerunning still changes `updated_at`, so it is not a no-op idempotent operation.
- It is limited to the 16 listed codes and does not directly update or delete `work_time_reports`.
- It does not update existing names in the conflict clause.
- It **does** overwrite `requires_order`, `is_absence`, and `is_system` for every existing row whose code matches, without checking current `is_system`, provenance, name, usage, or client customization.
- It inserts all missing proposed codes, even though eight of them were not previously canonical in the repository.
- No previous values are captured. Operational recovery would require a known-good backup or a manually prepared compensating data migration; a reliable rollback cannot be derived from this SQL alone.

Therefore it does not satisfy “safe code-based upgrade preserving custom types” and is not safe for the described production database as written.

## 10. Custom-type preservation assessment

**FAIL.** Unrelated custom codes outside the list are preserved, but custom/user-defined rows that share any listed code are not. The API historically creates arbitrary new codes with `isSystem=false`, so collision is permitted by the actual application. Production WKU is a known collision, and pre-feature tests explicitly describe OP as a custom type.

The statement that all custom types remain untouched is therefore materially false. Existing `work_time_reports` keep their foreign-key code, but their interpretation can change globally when the referenced dictionary flags are overwritten.

## 11. is_system assessment

Setting `is_system=true` is not a cosmetic normalization. In `backend/src/routes/work-time-types.ts:90-99,120-136` and the frontend dictionary:

- system records cannot be deleted;
- `requiresOrder` can no longer be edited;
- the UI disables deletion and hides the `requiresOrder` control.

The migration converts every colliding record, including the known non-system WKU and potentially client-owned OP/other codes, to this locked state. No requirement establishes that takeover. Existing established seed types `G/NDR/NS/UW/UOK/UŻ/L4` are already system types; forcing the flag adds no value for healthy records. For WKU and the additional eight codes, system ownership requires an explicit business/data-governance decision.

## 12. Seed/migration consistency

Fresh installations and upgraded installations converge on the same three flags for all 16 codes. They do **not** reliably preserve the same names:

- migration conflict handling preserves an existing name;
- `backend/prisma/seed.ts:73-83` subsequently upserts and overwrites `name` as well as all three flags;
- `backend/docker-entrypoint.sh:4-8` runs migration and then production seed at every backend start.

Thus the effective production upgrade overwrites client names for colliding codes even though the migration alone does not. Repeated starts also keep rewriting canonical fields/`updatedAt`. This is another failure of custom-record preservation.

## 13. Reconciliation assessment

The code change in `backend/src/routes/analytics.ts:619-641` correctly distinguishes:

- `requiresOrder=true`, no order: `Brak zlecenia`;
- `requiresOrder=false`, `isAbsence=false`, no order: `Typ nie jest nieobecnością i nie wymaga zlecenia`;
- an absence with an order included in closure: positive contribution and double-counting reason;
- an absence without an order included only in absence totals: zero contribution.

The signed-contribution calculation is unchanged, and the revised reason does not alter contribution values. Dynamic `isAbsence=true` aggregation will include WKU after the data correction.

- **Location:** branch history; `docs/business-rules.md` absence-calendar section
- **Exact problem:** feature is 12 commits behind current development and conflicts with v0.5.3 holiday documentation.

- **Required regression test:** run the full backend/frontend/build/lint/Prisma suite on the synchronized commit and add WKU coverage across holidays, weekends and company overrides.

### B2 — Critical — migration and production seed overwrite client-owned colliding records

- **Location:** migration lines 21-25; `backend/prisma/seed.ts:73-83`; `backend/docker-entrypoint.sh:4-8`
- **Exact problem:** code collision alone triggers replacement of flags and system ownership; the following seed also replaces names.
- **Why it matters:** it changes reporting semantics for all historical entries and can take away client edit/delete capabilities. WKU is a proven production example, and OP was explicitly treated as custom before this feature.
- **Required correction:** redesign migration/seed so approved WKU semantic fields are corrected without converting client ownership or overwriting client names; preserve custom/colliding rows unless an explicit, approved data rule identifies them as system-owned.
- **Required regression test:** execute migration plus seed on a disposable database containing custom WKU/OP/list-collision rows and historical reports, asserting exact allowed field changes, unchanged names/system ownership/custom rows, unchanged report rows, and safe repeated startup.

### B3 — High — canonical matrix and `is_system` expansion lack business authorization

- **Location:** migration values lines 12-20; seed lines 62-70; business/user documentation
- **Exact problem:** NN/NU/NUN/NUP/UB/UO/UPP have no pre-feature canonical definition; OP was custom; `is_system=true` for WKU and those codes is not required by the WKU decision.
- **Why it matters:** a technical assumption becomes irreversible client data governance and UI permissions behavior.
- **Required correction:** obtain and record an explicit business decision for each ambiguous code and separately for system ownership, or remove those codes/fields from automatic takeover. Keep the required WKU `false/true` correction narrowly scoped.
- **Required regression test:** data-driven tests for the approved matrix plus negative tests proving unapproved/custom codes remain unchanged and editable.

### B4 — High — migration test suite does not test migration effects

- **Location:** `backend/tests/canonical-work-time-types.test.ts:29-70`
- **Exact problem:** safety assertions are regex/string checks only and affirm the unsafe `is_system` update; no database-state transition is exercised.
- **Why it matters:** passing tests cannot detect the principal production failure mode.
- **Required correction:** add disposable-database migration/seed transition tests after the data strategy is corrected.
- **Required regression test:** fresh install, upgraded install, colliding custom rows, historical references, repeat run, and system/custom permission outcomes.
