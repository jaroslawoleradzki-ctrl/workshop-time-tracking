## 3. Primary gate — BLOCKER-2 / consistent snapshot

### Explicit answers

**A. Are totals and diagnostics derived from exactly the same logical dataset/database snapshot?**  
No.

`getClosureControlSummary()` performs these reads in sequence:

1. `getOrderReportRows()` reads closure orders and their reports (`analytics.ts:648-657`, helper query at `478-502`).
2. `workTimeType.findMany()` and `workTimeReport.findMany()` independently read absence types/reports (`660-682`).
3. `getEmployeeReportRows()` independently re-reads all active reports for employee totals (`723-729`, helper query at `251-265`).
4. Only after a mismatch is calculated, `getReconciliationDiagnostics()` independently re-reads all reports (`542-560`) and independently re-reads closure order IDs (`563-579`).

The records and order classification used for totals are therefore not the same fetched dataset used for diagnostics.

**B. If multiple database reads remain, what guarantees snapshot consistency?**  
Nothing. There is no transaction around `getClosureControlSummary()` and no database snapshot passed into its helpers. PostgreSQL's normal READ COMMITTED semantics permit each statement to observe a newer committed state.

**C. Is an appropriate Prisma transaction/isolation mechanism used?**  
No. The analytics implementation contains no `$transaction`, `RepeatableRead`, or `Serializable` mechanism. The only explicit transactions found in the reviewed source apply to report creation/copy-last-day, not reconciliation reads.

**D. Are totals and diagnostics derived from one fetched dataset?**  
No. At least six batch reads are used for a MISMATCHED summary after the unused diagnostics absence-type query was removed. XLSX additionally reads the order-report dataset once before invoking the summary, so it repeats the order query.

**E. Is there a final invariant assertion before returning MISMATCHED?**  
No. `analytics.ts:741-751` returns the response directly. It never rounds and compares `SUM(diagnostics.contribution)` with `difference`, and it has no controlled error/fallback when they disagree.

### Required response invariant

The implementation does not guarantee:

```text
round(SUM(diagnostics.contribution), 2)
===
round(totalSettledHours - totalEmployeeHours, 2)
```

The new tests at `analytics.test.ts:1127-1408` configure stable mocked return values and then compare the response fields. They prove selected stable examples only. They neither place the production reads in a shared snapshot nor simulate a state change between those reads.

### Concurrency behavior

All required interleavings remain unsafe:

- INSERT between totals and diagnostics: totals can remain at `-8`, while diagnostics sees an additional `-8` and sums to `-16`.
- UPDATE of hours/order/type between reads: employee/order/absence totals and diagnostics can observe different values or classifications.
- DELETE/soft-delete between reads: earlier totals may include the report while later diagnostics omits it, or the reverse.
- Order entering closure: an OPEN transition or CLOSED completion date moving into range can turn a later diagnostic contribution from negative to zero (or an absence contribution from zero to positive) without changing earlier totals.
- Order leaving closure: status/completion/soft-delete changes can produce the inverse inconsistency.
- Absence report order assignment change: an absence can move between zero and positive contribution between reads.
- `WorkTimeType.isAbsence` change: absence aggregation and later diagnostic classification can observe different dictionary states.

The issue also exists among the total reads themselves: order hours, absence hours, and employee hours do not share a snapshot.

**CONCURRENT SNAPSHOT SAFETY: FAIL**

**BLOCKER-2: UNRESOLVED**

## 4. Reconciliation functional math on stable data

For one stable, internally consistent dataset, the implemented per-record algebra is sound:

| Record classification | Contribution to `settled - employee` |
|---|---:|
| Non-absence with included order | 0 |
| Non-absence with missing/excluded order | `-hours` |
| Absence without included order | 0 |
| Absence with included order | `+hours` |

Verified behavior:

- Direction A: endpoint test returns `difference=-8`, one `-8` contribution.
- Direction B: endpoint test returns `difference=+16`, one `+16` contribution.
- Mixed: endpoint test returns `+16` and `-8`, sum `+8` equal to response difference.
- MATCHED: difference is zero and diagnostics is absent.
- Missing order: explicitly covered with reason `Brak zlecenia` and negative contribution.
- Order outside closure: implementation assigns negative contribution and reason `Zlecenie nieobjęte raportem zamknięcia`; no dedicated endpoint assertion was added.
- Absence without order: helper test verifies zero contribution/omission.
- Absence with included order: helper and endpoint examples verify positive contribution.
- Zero-hour and otherwise matched records: implementation assigns zero contribution and omits them. Creation API disallows new zero-hour records.
- Duplicates: implementation iterates every row, matching the additive behavior of totals; there is no inappropriate deduplication.
- Decimal/rounding: database hours are `Decimal(4,2)` and report difference uses two decimals. The stable algebra remains valid at report precision, although no new endpoint test specifically exercises decimal rounding.

The Direction B and Mixed endpoint mocks are not faithful single-dataset simulations: their mocked employee/order aggregates omit the absence row that their diagnostic query returns. They still exercise response identity and contribution sign, while the consistent helper example at `1674-1744` demonstrates the intended complete-record algebra. This weakens realism but does not change the stable mathematical conclusion.

**STABLE DATA MATH: PASS**

This result is deliberately separate from the failed concurrent-snapshot result.

## 14. Required rework before another approval review

1. Guarantee that all reconciliation totals and diagnostics are derived from one logical database snapshot, either from one fetched dataset or via an appropriate Prisma interactive transaction at `RepeatableRead`/stronger isolation with every helper using the transaction client.
2. Before returning MISMATCHED, round the contribution sum at report precision and assert it equals the returned difference; handle a violation explicitly rather than returning self-contradictory data.
3. Add a deterministic test that changes mocked database state between reads (or a multi-session PostgreSQL test) and proves the response invariant survives INSERT, UPDATE, soft-delete, closure membership, assignment, and classification changes.
4. Strengthen UI and XLSX tests to assert the omitted record identity/total fields, exact seven-column row, numeric cell types, and number formats.
5. Correct the remaining documentation/FINAL_REWORK claims and remove unrelated backend lockfile metadata churn.
