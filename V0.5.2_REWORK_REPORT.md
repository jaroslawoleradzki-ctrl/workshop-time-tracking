## 6. NS Root Cause
**REQUIRES PRODUCTION DATA CHECK**

The backend validation logic in `isWorkTimeReportAllowedOnCalendarDay()` correctly allows NS on non-working days when:
- `workTimeType.code !== 'G'` (true for NS)
- `!workTimeType.isAbsence` (true, NS has isAbsence: false)
- `workTimeType.requiresOrder` (true, NS requires order)
- `Boolean(orderId)` (true when valid order provided)

All backend tests pass including new test for Sunday 2026-09-06 with NS and valid order.

**Production-specific causes not reproducible in tests:**
- Production `WorkTimeType` NS configuration may differ from seed (`requiresOrder: false` or `isAbsence: true`)
- Company Calendar override for 2026-09-06 marking it as working day
- Frontend network/request issue specific to production environment
- Database transaction issue under load

**Safe production SELECT (no mutation):**
```sql
SELECT code, name, requires_order, is_absence, is_system, created_at, updated_at
FROM work_time_types
WHERE code IN ('G', 'NS')
ORDER BY code;

SELECT date, is_working_day, reason, created_at, updated_at
FROM company_calendar_days
WHERE date = DATE '2026-09-06';
```

**Expected seeded properties:**
| Property | Expected NS Value |
|---|---|
| `code` | `NS` |
| `name` | `Nadgodziny sobota/niedziela` |
| `requiresOrder` | `true` |
| `isAbsence` | `false` |
| `isSystem` | `true` |

## 9. Default G/NS Behavior

**Implementation:**
- `getDefaultWorkType(dateStr, workTypes)` returns 'NS' for weekends (Sat/Sun) if NS exists in workTypes, otherwise 'G'
- `resetForm(preserveWorkType)` uses dynamic default based on current date
- `currentDate` changes trigger form reset with appropriate default
- Editing existing entry preserves its workTimeTypeCode via `handleEditEntry`
- Manual type change remains until intentional form-resetting event (date/employee change)

**Company Calendar Override Behavior:**
| Scenario | Frontend Default | Backend Validation |
|---|---|---|
| Base calendar Saturday | NS | Allows NS+order, blocks G/absence |
| Saturday overridden to working day | NS | Allows all types (G, NS, absence) |
| Base calendar Monday | G | Allows all types |
| Monday overridden to day off | G | Blocks G/absence, allows NS+order |

**Design Decision:** Frontend uses simple weekday/weekend logic; backend enforces authoritative Company Calendar rules. This separation keeps frontend simple while backend validates.

## 10. Reconciliation Diagnostics Changes

**Backend (`backend/src/routes/analytics.ts`):**
- `getReconciliationDiagnostics()` now computes signed contribution per record:
  - Absence + orderInClosure: contribution = +hours (double-counted in settled)
  - Absence + no orderInClosure: contribution = 0 (counted in both)
  - Non-absence + orderInClosure: contribution = 0 (counted in both)
  - Non-absence + no order OR order not in closure: contribution = -hours (employee only)
- Returns `ReconciliationDiagnosticRecord[]` with `contribution` field
- Only includes records with non-zero contribution or explicit reason
- Removed unused `absenceTypeCodes` query

- Zero-hour records and matched records excluded

## 11. Diagnostics Sum Verification

**Test Case (verified by automated test):**
- Orders in closure: ord-1, ord-2
- Reports in date range:
  - emp-1: 40h G on ord-1 (in closure) → contribution = 0
  - emp-1: 16h UW on ord-1 (in closure) → contribution = +16 (double counted)
  - emp-1: 10h G on ord-2 (in closure) → contribution = 0
  - emp-1: 8h G no order → contribution = -8
  - emp-1: 4h UW no order → contribution = 0

- ordersHours = 40 + 16 + 10 = 66 (ALL reports on orders in closure)
- absenceHours = 16 + 4 = 20 (ALL absences)
- totalSettledHours = 66 + 20 = 86
- totalEmployeeHours = 40 + 16 + 10 + 8 + 4 = 78
- difference = 86 - 78 = 8

- Diagnostics sum = 0 + 16 + 0 + (-8) + 0 = 8 = difference ✓
