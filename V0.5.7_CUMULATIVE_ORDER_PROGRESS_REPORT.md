## Current and requested behaviour

Previously `getOrderReportRows` fetched only reports in the selected range and used their sum for `actualHours`, `deviation`, and `percent`.

`actualHours` remains the sum for the selected range. Progress values now use all non-deleted reports from the beginning of an order through the report's `dateTo`; reports after `dateTo` are not fetched.

## Start-date interpretation

`Order` has no `startDate`. It has `orderDate` (business date of the order) and `createdAt` (technical record timestamp). The implementation uses `orderDate` as the start of realization, normalized to its UTC business day. This avoids making progress depend on when an operator entered the record.

## Implementation and formulas

`getOrderReportRows` is the sole model used by the JSON endpoint and XLSX export. It loads non-deleted reports through `dateTo`, derives `periodActualHours` for the selected range, and derives internal `cumulativeActualHours` from `orderDate` through `dateTo`.

```text
actualHours = periodActualHours
deviation = plannedHours - cumulativeActualHours
percent = plannedHours > 0 ? cumulativeActualHours / plannedHours * 100 : 0
```

Existing two-decimal rounding and `plannedHours = 0` behaviour are retained. `cumulativeActualHours` is not added to the public API.

## Impact

- API: response shape unchanged; values of `deviation` and `percent` reflect cumulative progress.
- Frontend: no UI change. `ReportsView` displays API fields and its CSV builder serializes those same fields without recalculation.
- XLSX: uses `getOrderReportRows`, so it has the same values as JSON/UI.
- CSV: has the same values as UI/API.
- Closure report: uses the same row function; its period-based visibility and control totals continue to use `actualHours`.

## Tests and validation

The added regression scenario covers 30h in July, 20h in August, 10h in September, expecting August `actualHours=20`, `deviation=50`, and `percent=50`; it proves September is excluded. It also covers same-month CLOSED work, OPEN and SUSPENDED rows, soft-deleted reports, zero planned hours, `onlyWithHours`, closure-report reuse, and XLSX values. Existing tests cover the status-filter query behavior.

Backend focused analytics tests and backend build passed before final full-suite validation.

## Risks and known limitations

The selected business start is `orderDate`; historical records whose reported work predates that date are intentionally excluded from cumulative progress. This is consistent with the requested order-start interpretation. No migration is required.
