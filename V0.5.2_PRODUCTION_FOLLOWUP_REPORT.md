## 5. Root Cause of NS Bug
**The NS (Nadgodziny sobota/niedziela) bug could not be reproduced in the test environment.** 

Backend validation logic in `isWorkTimeReportAllowedOnCalendarDay()` correctly allows NS on non-working days when:
- `workTimeType.code !== 'G'` (true for NS)
- `!workTimeType.isAbsence` (true, NS has isAbsence: false)
- `workTimeType.requiresOrder` (true, NS requires order)
- `Boolean(orderId)` (true when valid order provided)

The existing test "allows overtime work entry on Saturday when requiresOrder=true AND orderId is provided" passes. A new test for Sunday 2026-09-06 with NS and valid order also passes.

**Possible production-specific causes not reproducible in tests:**
- Company Calendar override for 2026-09-06 marking it as working day (but G is blocked on Saturday, so unlikely)
- Production workTimeType NS configuration differs from seed (requiresOrder: false or isAbsence: true)
- Frontend network/request issue specific to production environment
- Database transaction issue under load

**Mitigation applied:** Added comprehensive test coverage for NS on weekends (both Saturday and Sunday) with valid orders, ensuring the validation logic is correct. Frontend error handling already displays backend validation errors.

## 9. Default Work Time Type Logic
**Implementation in `ReportingPanel.tsx`:**
- `getDefaultWorkType(dateStr, workTypes)` returns 'NS' for weekends (Sat/Sun), 'G' for weekdays
- `resetForm(preserveWorkType)` uses dynamic default based on current date
- `currentDate` changes trigger form reset with appropriate default
- Editing existing entry preserves its workTimeTypeCode (via `handleEditEntry`)

**Company Calendar Overrides:**
- Frontend uses basic weekend/weekday logic (Sat/Sun → NS, Mon-Fri → G)
- Backend validation uses Company Calendar for actual permission checks
- If admin marks Saturday as working day: frontend defaults to NS, but backend allows G
- If admin marks weekday as day off: frontend defaults to G, but backend blocks G/absence
- This separation keeps frontend simple while backend enforces authoritative rules

## 10. Company Calendar Override Behavior
| Scenario | Frontend Default | Backend Validation |
|----------|------------------|-------------------|
| Base calendar Saturday | NS | Allows NS+order, blocks G/absence |
| Saturday overridden to working day | NS | Allows all types (G, NS, absence) |
| Base calendar Monday | G | Allows all types |
| Monday overridden to day off | G | Blocks G/absence, allows NS+order |

## 12. Reconciliation Diagnostics Implementation
**New function `getReconciliationDiagnostics()` in `analytics.ts`:**
- Fetches all workTimeReports in date range with employee, order, workTimeType
- Gets orders in closure report (OPEN + CLOSED with completionDate in range)
- Gets absence type codes (isAbsence: true)
- Identifies reports NOT in reconciliation:
  - Non-absence without orderId → "Brak zlecenia"
  - Non-absence with orderId not in closure report → "Zlecenie nieobjęte raportem zamknięcia"

**Extended `getClosureControlSummary()` to return `ClosureControlSummaryWithDiagnostics`:**
- Includes `diagnostics: ReconciliationDiagnosticRecord[]` when status = MISMATCHED
- Diagnostics contain: employeeName, date, workTimeTypeCode, workTimeTypeName, hours, orderNumber, reason

## 16. Performance Impact
- **Diagnostic query**: Single `workTimeReport.findMany` with includes (employee, order, workTimeType) - batched
- **Orders in closure**: Single `order.findMany` with select id - batched
- **Absence types**: Single `workTimeType.findMany` - batched
- **All diagnostics computed in memory** - no N+1 queries
- **Only runs when status = MISMATCHED** - no overhead for matched months
- **Reuses data already fetched** for closure control summary
- Expected impact: <50ms for typical month (thousands of entries)
