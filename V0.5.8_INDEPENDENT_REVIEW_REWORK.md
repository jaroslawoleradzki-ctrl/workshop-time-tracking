## Scope

This rework addresses only the independent-review findings FRONT-001 and DOC-001. It does not implement retry or cache-expiry behavior from OBS-001. Current development was re-fetched before changes and remains the already integrated v0.5.7 baseline; no additional integration was needed.

## FRONT-001 root cause

The previous form-reset effect depended on `calendarDecision`. A response for the current date therefore retriggered `resetForm`, even after a user had manually selected a type, entered form data, or started editing a saved report. In addition, `resetForm` could use the previous date's `calendarDecision` when the new date was not yet cached.

## Implementation correction

`ReportingPanel` now:

- tracks whether the form is `pristine`, `modified`, or `editing` in component-local refs;
- resets a new form only when its employee/date context changes, not when a calendar response arrives;
- uses a cached decision only when its `date` exactly matches `currentDate`;
- leaves the work-time type blank while an uncached date's decision is unresolved;
- applies a calendar-aware default only when the response belongs to the current date and the form remains pristine;
- marks direct work-type, order, hours, and missing-card changes as modified; and
- marks an edit form before loading its saved data, so a current-date response cannot cancel edit mode or replace saved fields.

The calendar fetch race guard remains in place. The endpoint-failure fallback cache behavior was deliberately not changed.

## Regression tests added

Four deterministic deferred-response tests were added in `frontend/src/test/ReportingPanel.test.tsx`:

1. A manual work-time selection survives a delayed response for the current date.
2. An edit form retains type, order, hours, missing-card flag, and edit mode after a delayed response for the current date.
3. A cached prior-date decision is not applied while an uncached new date is unresolved; the new date receives its correct default after resolution.
4. A pristine new form receives the correct asynchronous calendar default.

The existing stale **old**-date response regression remains unchanged and passes.

## DOC-001 correction

`docs/user-guide.md` now documents the calendar-aware default rules: ordinary working weekday -> `G`; ordinary weekend -> `NS` when available; public holiday/company day off -> blank; company working weekend -> `G`; missing `G`/`NS` -> blank. It also states that users may select another permitted type and that edit mode preserves saved type, order, hours, and missing-card state.
