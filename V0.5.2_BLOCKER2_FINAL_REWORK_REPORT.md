## 1. Dokładna przyczyna BLOCKER-2 (Root Cause)

W dotychczasowej implementacji funkcja `getClosureControlSummary()` w pliku `backend/src/routes/analytics.ts` wyliczała sumy kontrolne oraz diagnostykę rozliczenia poprzez serię niezależnych odczytów Prisma:
1. `getOrderReportRows()` pobierało zlecenia i raporty zleceń,
2. `prisma.workTimeType.findMany()` i `prisma.workTimeReport.findMany()` pobierały nieobecności,
3. `getEmployeeReportRows()` osobno odczytywało wszystkie raporty pracowników,
4. W przypadku niezgodności `getReconciliationDiagnostics()` wykonywało kolejne zapytania do bazy o raporty i zlecenia.

Przy domyślnym poziomie izolacji PostgreSQL (`READ COMMITTED`), każda operacja odczytu mogła widzieć nowszy stan bazy danych. Współbieżne operacje `INSERT`, `UPDATE`, soft-delete lub zmiany statusu/terminu zlecenia w trakcie generowania raportu mogły prowadzić do sytuacji, w której wyliczona różnica kontrolna (`totalSettledHours - totalEmployeeHours`) nie była równa sumie wkładów rekordów diagnostycznych (`SUM(diagnostics.contribution)`).

## 2. Zastosowane rozwiązanie: Spójna migawka transakcyjna (Consistent Snapshot)

### A. Strategia izolacji transakcji
Funkcja `getClosureControlSummary()` została objęta interaktywną transakcją Prisma z poziomem izolacji `RepeatableRead`:
```typescript
if ('$transaction' in client && typeof client.$transaction === 'function') {
  return (client as PrismaClient).$transaction(
    async (tx) => runCalculation(tx),
    {
      isolationLevel: Prisma.TransactionIsolationLevel.RepeatableRead,
      maxWait: 10_000,
      timeout: 30_000,
    },
  );
}
```
Poziom izolacji `RepeatableRead` w PostgreSQL gwarantuje, że wszystkie zapytania wewnątrz transakcji widzą dokładnie tę samą migawkę bazy danych (stan zatwierdzony przed wykonaniem pierwszego zapytania w transakcji).

### B. Konwersja funkcji pomocniczych (Helper Functions)
Wszystkie funkcje pomocnicze przyjmują opcjonalny klient bazodanowy `db: DbClient = prisma` (`DbClient = PrismaClient | Prisma.TransactionClient`) i wykonują wszystkie zapytania wyłącznie przez przekazanego klienta transakcyjnego `tx`:
- `getOrderReportRows(filters, db = prisma)` -> `db.order.findMany(...)`
- `getEmployeeReportRows(filters, db = prisma)` -> `db.workTimeReport.findMany(...)`
- `getAbsencePeriodRows(filters, db = prisma)` -> `db.workTimeReport.findMany(...)`
- `getReconciliationDiagnostics(filters, db = prisma)` -> `db.workTimeReport.findMany(...)`, `db.order.findMany(...)`
- `getClosureControlSummary(filters, client = prisma)` -> przekazuje `tx` do wszystkich wywołań wewnątrz transakcji.

## 3. Implementacja serwerowego strażnika niezmiennika (Server-Side Invariant Guard)

Przed zwróceniem odpowiedzi ze statusem `MISMATCHED`, funkcja `getClosureControlSummary()` weryfikuje niezmiennik spójności:
```typescript
const diagnosticsContributionTotal =
  Math.round(diagnostics.reduce((sum, d) => sum + d.contribution, 0) * 100) / 100;
const expectedDifference = difference;

if (diagnosticsContributionTotal !== expectedDifference) {
  logger.error(
    {
      dateFrom,
      dateTo,
      totalSettledHours,
      totalEmployeeHours,
      difference,
      diagnosticsContributionTotal,
      diagnosticsCount: diagnostics.length,
    },
    'Naruszenie niezmiennika spójności diagnostyki rozliczenia (reconciliation invariant violation)',
  );
  throw new ReconciliationConsistencyError(
    'Błąd spójności danych raportu rozliczenia: suma wkładów diagnostyki nie odpowiada wyliczonej różnicy kontrolnej.',
  );
}
```

W handlerze endpointu `GET /api/analytics/closure-control-summary`:
- Błąd `ReconciliationConsistencyError` jest logowany ze szczegółami po stronie serwera.
- Do klienta zwracany jest kontrolowany błąd HTTP 500 z kodem `RECONCILIATION_CONSISTENCY_ERROR` i bezpiecznym komunikatem biznesowym, bez ujawniania wewnętrznej struktury bazy danych.
