# V0.5.4 Client Regression - Root Cause Analysis

## ROOT CAUSE

The reconciliation logic in `getReconciliationDiagnostics()` and `getOrderReportRows()` determines "orders in closure" based on the **CURRENT** order status at query time, not the status during the report period.

**Exact condition causing the regression** (backend/src/routes/analytics.ts:582-598 and 501-505):

```typescript
// BOTH functions use this logic:
OR: [
  { status: OrderStatus.OPEN },
  {
    status: OrderStatus.CLOSED,
    completionDate: {
      gte: new Date(`${dateFrom}T00:00:00.000Z`),
      lte: new Date(`${dateTo}T23:59:59.999Z`),
    },
  },
]
```

An order is considered "in closure" only if:
- It is currently `OPEN`, OR
- It is `CLOSED` with `completionDate` **within** the report date range

**What happens with order 530-8-49:**
- August 2026: Order is `OPEN`, 35h logged → included in closure → report MATCHED
- 2026-09-10: Order closed → status = `CLOSED`, `completionDate` = 2026-09-10
- Report for August 2026 re-run: Order now `CLOSED` with `completionDate` **outside** range (2026-09-10 > 2026-08-31) → **EXCLUDED** from closure
- Hours still counted in `totalEmployeeHours` but NOT in `ordersHours` → **-35h difference**
- Diagnostic: `"Zlecenie nieobjęte raportem zamknięcia"` (Order not covered by closure report)

## INTRODUCED BY COMMIT / CHANGE

**The core logic bug EXISTS in BOTH v0.5.3 and v0.5.4.** It was NOT introduced in v0.5.4.

**Only change in analytics.ts between v0.5.3 → v0.5.4** (commit `7180f51` / `0f1b13f` area):
```diff
-        reason = !orderId ? 'Brak zlecenia' : 'Zlecenie nieobjęte raportem zamknięcia';
+        if (orderId) {

+        } else {

```

**v0.5.4 only improved the diagnostic message accuracy** (from generic "Brak zlecenia" to specific "Zlecenie nieobjęte raportem zamknięcia"). This made the existing bug more visible/diagnosable.

## WHY 35H DISAPPEARS

1. **Before closure (2026-09-10)**: Order 530-8-49 status = `OPEN` → included in `ordersInClosure` → its 35h (logged in August) counted in `ordersHours` (settled side) → `totalSettledHours` = `totalEmployeeHours` → **MATCHED**

2. **After closure**: Order status = `CLOSED`, `completionDate` = 2026-09-10 → **excluded** from `ordersInClosure` (completionDate > 2026-08-31) → 35h **removed from `ordersHours`** but **still in `totalEmployeeHours`** → `difference` = -35h → **MISMATCHED**

3. **Diagnostic output**: Each of the 35h entries gets `contribution = -hours`, `reason = "Zlecenie nieobjęte raportem zamknięcia"`

---

## EXPECTED BUSINESS LOGIC

**Business Rule (from user):** *"Raport za zamknięty okres powinien być historycznie stabilny. Zmiana statusu zlecenia po dateTo raportu nie może zmieniać klasyfikacji godzin, które należą do raportowanego okresu."*

**Correct criterion for historical closure report:**
> An order belongs to the closure report for period [dateFrom, dateTo] **if it has ANY workTimeReport entries within that date range**, regardless of its current status or completionDate.

**Rationale:** Hours were worked and recorded during that period. The order was active (OPEN) at that time. Closing it later cannot retroactively remove those hours from the historical reconciliation.

## TEST GAP

**Existing tests cover:**
- `ZL-003`: CLOSED, completionDate IN range, hours IN range → visible
- `ZL-004`: CLOSED, completionDate IN range, no hours → visible (0h)
- `ZL-005`: CLOSED, completionDate BEFORE range → hidden
- `ZL-006`: CLOSED, completionDate AFTER range, **NO hours in range** → hidden
- `ZL-007`: CLOSED, completionDate IN range, hours OUTSIDE range → visible (0h)

**MISSING TEST CASE (would catch this regression):**
- `CLOSED`, `completionDate` **AFTER** range, **HOURS IN range** → should be visible with actual hours

**Why tests didn't detect it:** No test exists for an order closed AFTER the report period that has hours INSIDE the report period. The test `ZL-006` has completionDate after range but **no hours in range**, so it correctly expects hidden.

## RECOMMENDED MINIMAL FIX

Modify the `ordersInClosure` query in BOTH functions to also include orders that have work time reports in the date range:

```typescript
// In getReconciliationDiagnostics (lines 582-598):
const ordersInClosure = await db.order.findMany({
  where: {
    deletedAt: null,
    OR: [
      { status: OrderStatus.OPEN },
      {
        status: OrderStatus.CLOSED,
        completionDate: {
          gte: new Date(`${dateFrom}T00:00:00.000Z`),
          lte: new Date(`${dateTo}T23:59:59.999Z`),
        },
      },
      // ADD: Orders with reports in range (historical activity)
      {
        reports: {
          some: {
            deletedAt: null,
            date: {
              gte: new Date(`${dateFrom}T00:00:00.000Z`),
              lte: new Date(`${dateTo}T23:59:59.999Z`),
            },
          },
        },
      },
    ],
  },
  select: { id: true },
});

// In getOrderReportRows (lines 501-505) - same OR condition:
OR: filters.closureReport
  ? [
      { status: OrderStatus.OPEN },
      { status: OrderStatus.CLOSED, completionDate: completionDateRange },
      // ADD:
      {
        reports: {
          some: {
            deletedAt: null,
            date: reportDateRange,
          },
        },
      },
    ]
  : undefined,
```

---

## RISK OF FIX

| Risk | Assessment |
|------|------------|
| **False positives** | Low. Only adds orders that actually have reports in the period. |
| **Performance** | Negligible. Adds one `EXISTS` subquery on indexed `orderId` + `date`. |
| **Double counting** | None. Reports are still filtered by `reportDateRange` when summing hours. |
| **Edge case: Order closed BEFORE range with hours in range** | Impossible - if closed before range, no new reports can be added in range (completionDate < dateFrom). |
| **Edge case: Deleted reports** | Handled by `deletedAt: null` filter on reports. |

## ROOT CAUSE CONFIRMED: YES

**Exact condition in code:**
```typescript
// backend/src/routes/analytics.ts:585-594 (getReconciliationDiagnostics)
// backend/src/routes/analytics.ts:502-504 (getOrderReportRows)
OR: [
  { status: OrderStatus.OPEN },
  {
    status: OrderStatus.CLOSED,
    completionDate: { gte: dateFrom, lte: dateTo },
  },
]
```

**Commit that introduced the logic:** Not in v0.5.3→v0.5.4. The logic predates both versions. The v0.5.4 change (diagnostic message improvement) merely exposed it.

**Verification:** The bug exists in v0.5.3 tag - same `ordersInClosure` query logic. Client encountered it after upgrading to v0.5.4 because they closed an order post-period for the first time, and the improved diagnostic message made it clearly identifiable.
