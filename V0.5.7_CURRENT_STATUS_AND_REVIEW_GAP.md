## Implementation assessment

### Backend and API

`getOrderReportRows()` loads active related reports only through `dateTo`, calculates `periodActualHours` by selected range, and calculates `cumulativeActualHours` after the normalized `orderDate`. The JSON route `GET /api/analytics/report-by-order` and `GET /api/analytics/export/by-order` both call that one helper. The public row shape is unchanged; only `deviation` and `percent` intentionally change semantic meaning from period to cumulative values.

The cumulative helper presently omits v0.5.6's additional closure `OR` branch. Consequently, in closure mode, a CLOSED order whose `completionDate` moved beyond the selected range can be excluded even when it has period work. That creates the historical reconciliation failure fixed by v0.5.6. `getReconciliationDiagnostics()` likewise lacks the matching membership predicate, so the v0.5.6 consistency guarantee is absent from this branch.

### Frontend, filtering, authorization, and history

No frontend source changed for v0.5.7. `ReportsView.tsx` supplies the existing filters and displays/export-serializes `actualHours`, `deviation`, and `percent` supplied by the API. This preserves UI/CSV parity. `onlyWithHours` remains based on period hours, which correctly hides historical-only rows for a selected period. Order-number and status filters remain server-side; closure mode continues to ignore incompatible status and only-with-hours filters.

No route authentication, role check, authorization scope, schema, migration, seed, or environment contract changed. The report routes already use the existing JWT middleware; v0.5.7 adds no authorization behavior.

Historical data is read only. Active reports are qualified by `deletedAt: null`; future reports are excluded by the `dateTo` upper bound. The material historical-data risk is the missing v0.5.6 closure predicate, not mutation or data loss.
